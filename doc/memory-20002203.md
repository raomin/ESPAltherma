# Hydro board software 20002203: what its RAM holds

Software 20002203 runs the 4-8 kW EHVH/EHVX/EHVZ/EHBH/EHBX E, EA and EJ series (Altherma 3 R), the 9-16 kW EBLA/EDLA monoblocs and the EWAA/EWYA chillers. Everything below was read on an **EHBX08EF6V** with an ERGA06EVH outdoor unit (November 2026), with the **Memory read** of the diagnostics page (command `R`, nothing written): single reads against the user interface, and three dumps of the whole address space a few hours apart (7 November 19:40, 8 November 11:45 and 18:40) to see what moves. Addresses are RAM addresses of the hydro board.

## Used by ESPAltherma

| Address | Type | What | How it was checked |
| ------- | ---- | ---- | ------------------ |
| `0x3470` / `0x34AE` | word, value × 256 | hot water curve, mild / cold point | equal to the interface's settings |
| `0x3472` / `0x34B0` | word, value × 256 | leaving water curve, mild / cold point (`[1-03]` / `[1-02]`) | 25 / 38 as set; a write changes the target at once |
| `0x2EE8` | word, value × 256 | the hot water target the thermostat aims for | equal to *DHW setpoint* |
| `0x2F3C` | word, value × 256 | the leaving water target the thermostat aims for, **shift included** | 37 written with a +10 K shift on the interface read 47 |
| `0x4E70` | byte | power limitation, `[4-08]`: 0 none, 1 continuous, 2 digital inputs | 2, as the unit's settings export says |
| `0x4E71` | byte | `[4-09]`, kind: 1 = kW | 1 |
| `0x3476` | float | `[5-09]`, limit 1 in kW | 20.0 |
| `0x4E50` | byte | `[5-05]`, limit 1 in A | 50 |
| `0x41A8` / `0x41AC` | float | active limit (kW / A) | |
| `0x08E6` | 32-bit count | **heat produced** since the installation, kWh, all modes (*Unit meter: Heat produced*) | the sum of the three heat counts below, to the kWh; the same count as a float at `0x3756` |
| `0x36B2` | 32-bit count | compressor hours, space heating | 3240, as *Information > Operating hours* |
| `0x3696` | 32-bit count | compressor hours, space cooling | 251, as the interface |
| `0x3650` | 32-bit count | compressor hours, hot water | 691, as the interface |
| `0x3692` | 32-bit count | pump hours | 4552, as the interface |
| `0x3752` | 32-bit count | **compressor starts** | one more for each start seen between reads (the compressor's frequency), none while it stood; 2753 starts in 4187 compressor hours; the sum of the three per-mode counts `0x36BA` + `0x369E` + `0x3658` |

They go to MQTT and Home Assistant next to the heat produced, read once a minute: `Unit meter: Compressor hours, space heating (h)` and so on, `Unit meter: Pump hours (h)`, `Unit meter: Compressor starts` (lifetime totals). Just after a power-up the board answers before it has loaded its counts, which read 0 for a minute or so: nothing is published until the heat count is back (a lifetime total at 0 and back would count twice in Home Assistant's statistics), and a lifetime count never goes below one already read. The counts are 32-bit (the software loads each from a slot of its persistent block at start, in one function that names them all): the same slots in every other hydro board software gave the addresses for those, [doc/control.md](control.md#the-units-own-energy-meter-and-counters).

## Energy metering, found but not used yet

Each count below moves only in its own mode between the dumps, and the counts add up: the three heat counts make `0x08E6`, the electricity counts make `0x08E2`.

| Address | Type | Value read (8 November, 18:40) | What it is |
| ------- | ---- | ------------------------------ | ---------- |
| `0x36C2` | float, kWh | 12940.6 | heat produced, **space heating**: the interface's *Produced heat* (below) |
| `0x3664` | float, kWh | 4881.8 | heat produced, **hot water**: +7.9 kWh over one tank load, unchanged overnight while only the house was heated |
| `0x36A6` | float, kWh | 915.0 | heat produced (removed), **cooling**: still in November |
| `0x3722` | 32-bit count, Wh | 2708262 | electricity, **space heating** |
| `0x3702` | 32-bit count, Wh | 1362763 | electricity, **hot water**: +2.8 kWh over that tank load |
| `0x36FA` | 32-bit count, Wh | 153516 | electricity, **cooling** |
| `0x371A` | 32-bit count, Wh | 47093 | electricity, **backup heater in space heating**: part of the interface's electricity input (below) |
| `0x370A`, `0x3712` | 32-bit count, Wh | 0, 0 | two more, unused on this unit |
| `0x08CE` … `0x08DE` | 32-bit counts, kWh | 47, 0, 2708, 154, 1363 | the same electricity counts in whole kWh: backup heater, (unused), space heating, cooling, hot water |
| `0x08E2` | 32-bit count, kWh | 4272 | electricity, **all modes**: 47 + 0 + 2708 + 154 + 1363 |

The interface's **Energy data → Since installation** shows the space heating figures: *Produced heat* is `0x36C2` (12940 while it read 12940.6) and *Electricity input* is `0x3722` + `0x371A`, the heat pump and the backup heater (2755 while they made 2755.4). With hot water and cooling, the unit made 18736 kWh of heat from 4272 kWh of electricity: a seasonal COP of 4.39 since the installation (space heating 4.70 with the backup heater, hot water 3.58, cooling 5.96).

## Other findings

| Address | Type | Value read | What it seems to be |
| ------- | ---- | ---------- | ------------------- |
| `0x362E`, `0x36AA` | 32-bit count | 39, 39 | the interface's *Booster heater* and *BUH space heating* hours, 39 h each (which is which: not known yet) |
| `0x36AE` | 32-bit count | 11 | the interface's *BUH additional capacity space heating* hours (11 h); its *BUH tank* and *BUH additional capacity tank* read 0 h |
| `0x36BA`, `0x369E`, `0x3658` | 32-bit count | 1803, …, … | the compressor starts in space heating, cooling and hot water (their sum is `0x3752`) |
| `0x36B6`, `0x36BE` | 32-bit count | 1803, 3386 | more counts, not among the interface's running hours; `0x36BE` rises with the space heating hours |
| `0x2D96` … `0x2DA8` | words, value × 256 | 6.0 5.5 5.5 5.5 7.0 7.5 7.0 8.0 9.0 (20:45) | the outdoor temperature's history in slots of about 20 minutes, newest first: the software resets `0x2D96` to `0x7FFF` at each new slot and then keeps the **lowest** outdoor temperature of the slot there (so it reads 327.99 for one cycle, then the slot's minimum), and shifts the slots down |
| `0x0910` … `0x0915` | bytes | `06 12 27 1a 0b 08` | the unit's clock: weekday (Monday 0), hour, minute, year, month, day (Sunday 18:39, 8.11.2026; 20:43 two hours later) |
| `0x0900` … `0x0DFF` | | | what the board keeps across restarts: the model name at `0x0968` (the memory's offset 0: ESPAltherma reads it on every board with the memory read, as `Unit model`), the counts above packed from `0x0BA0`; a second copy at `0x5562` |
| `0x8000` … `0xC3FF` | | | random-looking bytes that never change; `0xC400` … `0xFFFF` is empty |

The outdoor temperature in this history keeps up while the heat pump is idle, unlike the outdoor unit's `R1T-Outdoor air temp.` ESPAltherma reads today: that one stood at 9.5 °C from the compressor's stop for four hours, while the interface and this history went down to 6 °C. The word the board itself works with is the one it compares `0x2D96` against (`0x1E3C` in the software), not published yet.

No history of the energy (the week's histograms of the interface) was found: nothing shifted at midnight between the dumps, so the interface seems to keep it itself.
