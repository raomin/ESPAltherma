# Hydro board software 20002203: what its RAM holds

Software 20002203 runs the 4-8 kW EHVH/EHVX/EHVZ/EHBH/EHBX E, EA and EJ series (Altherma 3 R), the 9-16 kW EBLA/EDLA monoblocs and the EWAA/EWYA chillers. Everything below was read on an **EHBX08EF6V** with an ERGA06EVH outdoor unit (November 2026), with the **Memory read** of the diagnostics page (command `R`, nothing written): single reads against the user interface, and three dumps of the whole address space a few hours apart (7 November 19:40, 8 November 11:45 and 18:40) to see what moves. Addresses are RAM addresses of the hydro board.

## Used by ESPAltherma

| Address | Type | What | How it was checked |
| ------- | ---- | ---- | ------------------ |
| `0x3470` / `0x34AE` | word, value × 256 | hot water curve, mild / cold point | equal to the interface's settings |
| `0x3472` / `0x34B0` | word, value × 256 | leaving water curve, mild / cold point (`[1-03]` / `[1-02]`) | 25 / 38 as set; a write changes the target at once |
| `0x2EE8` | word, value × 256 | hot water target, recomputed on every pass as the lower of `0x2F50` (current phase target) and `0x3160` (heat pump maximum) | equal to *DHW setpoint*; a direct RAM write is replaced within about half a second (measured), in fixed or weather-dependent mode |
| `0x2F3C` | word, value × 256 | the leaving water target the thermostat aims for, **shift included** | 37 written with a +10 K shift on the interface read 47 |
| `0x4E70` | byte | power limitation, `[4-08]`: 0 none, 1 continuous, 2 digital inputs | 2, as the unit's settings export says |
| `0x4E71` | byte | `[4-09]`, kind: 1 = kW | 1 |
| `0x3476` | float | `[5-09]`, limit 1 in kW | 20.0 |
| `0x4E50` | byte | `[5-05]`, limit 1 in A | 50 |
| `0x41A8` / `0x41AC` | float | active limit (kW / A) | |
| `0x08E6` | 32-bit count | **heat produced** since the installation, kWh, all modes (*Unit meter: Heat produced*) | the sum of the three heat counts below, to the kWh; the same count as a float at `0x3756` |
| `0x36B2` | 32-bit count | compressor hours, space heating | 3240, as *Information > Operating hours* |
| `0x3696` | 32-bit count | compressor hours, space cooling | 251, as the interface |
| `0x3650` | 32-bit count | compressor hours, hot water | 691, as the interface |
| `0x3692` | 32-bit count | pump hours | 4552, as the interface |
| `0x3752` | 32-bit count | **compressor starts** | one more for each start seen between reads (the compressor's frequency), none while it stood; 2753 starts in 4187 compressor hours; the sum of the three per-mode counts `0x36BA` + `0x369E` + `0x3658` |

They go to MQTT and Home Assistant next to the heat produced, read once a minute: `Unit meter: Compressor hours, space heating (h)` and so on, `Unit meter: Pump hours (h)`, `Unit meter: Compressor starts` (lifetime totals). Just after a power-up the board answers before it has loaded its counts, which read 0 for a minute or so: nothing is published until the heat count is back (a lifetime total at 0 and back would count twice in Home Assistant's statistics), and a lifetime count never goes below one already read. The counts are 32-bit (the software loads each from a slot of its persistent block at start, in one function that names them all): the same slots in every other hydro board software gave the addresses for those, [doc/control.md](control.md#the-units-own-energy-meter-and-counters).

## Energy metering, found but not used yet

Each count below moves only in its own mode between the dumps, and the counts add up: the three heat counts make `0x08E6`, the electricity counts make `0x08E2`. ESPAltherma publishes the three heat floats, `0x08E2` and the four electricity counts in Wh as `Unit meter: Heat produced, space heating (kWh)` … `Unit meter: Electricity used, backup heater (kWh)`, read with the other counters.

| Address | Type | Value read (8 November, 18:40) | What it is |
| ------- | ---- | ------------------------------ | ---------- |
| `0x36C2` | float, kWh | 12940.6 | heat produced, **space heating**: the interface's *Produced heat* (below) |
| `0x3664` | float, kWh | 4881.8 | heat produced, **hot water**: +7.9 kWh over one tank load, unchanged overnight while only the house was heated |
| `0x36A6` | float, kWh | 915.0 | heat produced (removed), **cooling**: still in November |
| `0x3722` | 32-bit count, Wh | 2708262 | electricity, **space heating** |
| `0x3702` | 32-bit count, Wh | 1362763 | electricity, **hot water**: +2.8 kWh over that tank load |
| `0x36FA` | 32-bit count, Wh | 153516 | electricity, **cooling** |
| `0x371A` | 32-bit count, Wh | 47093 | electricity, **backup heater in space heating**: part of the interface's electricity input (below) |
| `0x370A`, `0x3712` | 32-bit count, Wh | 0, 0 | two more, unused on this unit |
| `0x08CE` … `0x08DE` | 32-bit counts, kWh | 47, 0, 2708, 154, 1363 | the same electricity counts in whole kWh: backup heater, (unused), space heating, cooling, hot water |
| `0x08E2` | 32-bit count, kWh | 4272 | electricity, **all modes**: 47 + 0 + 2708 + 154 + 1363 |

The interface's **Energy data → Since installation** shows the space heating figures: *Produced heat* is `0x36C2` (12940 while it read 12940.6) and *Electricity input* is `0x3722` + `0x371A`, the heat pump and the backup heater (2755 while they made 2755.4). With hot water and cooling, the unit made 18736 kWh of heat from 4272 kWh of electricity: a seasonal COP of 4.39 since the installation (space heating 4.70 with the backup heater, hot water 3.58, cooling 5.96).

The word the board itself works with is the one it compares `0x2D96` against (`0x1E3C` in the software), not published yet.

## Field settings

The installer's field settings are in RAM in the image of the board's persistent memory: **RAM `0x0968` + memory index**, the same index ESPAltherma's control uses (278, 366, 367, 372–374), one byte each: **(value − minimum of its range) << 2**, plus two flag bits (3 here). The image starts with the model name (`EHBX08EF6V` at `0x0968`, index 0); a second copy sits at `0x55CA`. Found by changing settings on the interface, comparing the RAM and the settings export (`db-export.ini`) before and after, and setting them back (9 November 2026): every byte below moved with its setting and came back to its first value.

Settings whose range starts at another setting are stored relative to it, and re-encoded when it changes: the leaving water curve relative to `[9-01]`, the cooling curve relative to `[9-03]`. Indices 456–459 (`0x0B30`–`0x0B33`) changed as well, by +3, +3, −3, −3, and back, without a setting of theirs being changed: most likely other settings relative to `[9-01]` and `[9-03]`.

Elsewhere in RAM: the ranges the board derives from these settings sit in the limit records ESPAltherma reads (`0x4FB7`/`0x4FB8` span and minimum of the leaving water curve, 41/15 → 37/18), and the tank's ON hysteresis `[6-00]` is a word of value × 256 at `0x344C`, copied to `0x30E6` and `0x3136` (5 → 6 with the setting, and a RAM write of `0x344C` reached both copies within a second). An earlier version of this page took `0x30E6` for the interface's shift: the shifts are in the operation bytes below, and `0x30E6` did not move when the heating shift changed. The words from about `0x3460` that hold the curves ESPAltherma writes and the power limits did not follow the other settings: they are working values, not the settings.

No history of the energy (the week's histograms of the interface) was found: nothing shifted at midnight between the dumps, so the interface seems to keep it itself.

## Operation: on/off and heating/cooling, read only

Space heating/cooling on or off, hot water on or off and the operating mode are in the same image, at three indices. Found by switching through six states from the Daikin cloud (Onecta, through the user interface) and reading the image and its second copy after each change; every change reached the image within one or two minutes (9 November 2026).

| State (space, hot water) | Index 61 (`0x09A5`) | Index 77 (`0x09B5`) | Index 278 (`0x0A7E`) | RAM `0x0901` |
| --- | --- | --- | --- | --- |
| heating, hot water off | 17 | 20 | 26 | 0 |
| heating, hot water on | 17 | 28 | 26 | 64 |
| off, hot water on | 17 | 8 | 26 | 64 |
| cooling, hot water on | 34 | 28 | 26 | 64 |
| automatic heating/cooling, hot water on | 17 | 28 | 58 | 64 |
| off, hot water off | 17 | 0 | 26 | 0 |

- **Index 77, on/off:** +8 hot water on, +20 space heating/cooling on; +128 while a scheduled disinfection runs (156 from its start at 11:00 on 17 November until it was switched off). ESPAltherma reads this bit as *Disinfection running*.
- **Index 61, operating mode:** 17 heating, 34 cooling. In automatic mode the unit picks one itself, here heating at 8 °C outdoors.
- **Index 278:** bit 5 (+32) set in automatic heating/cooling mode. This is the byte whose low bits ESPAltherma already reads as the setpoint modes.
- **RAM `0x0901`:** bit 6 is a working copy of "hot water on", outside the image.
- **Not part of the mode:** `0x0912` counts up at every change.
- **The interface's shifts** (17 November), one byte each, sign in bit 4 and the value in the bits below (not shifted like the field settings): index 68 (`0x09AC`) heating shift of the main zone (2 → 5 → 2, a copy at `0x0924`), index 69 (`0x09AD`) heating shift of the additional zone (0 → 3 → 0), index 70 (`0x09AE`) cooling shift of the main zone (−8 = 24, −10 = 26, +3 = 3, a copy at `0x0926`).

**They cannot be set over X10A.** Tried on the same unit, one byte at a time, with index 77 (hot water on → off) and `0x0901`; each was put back afterwards:

- **Persistent memory (`E` command, as for the curve):** the write is acknowledged, and the memory read (`I`) gives the new value back. The image, the unit and the cloud stayed as they were for five minutes. Written back at once: left there, the unit would have come up with hot water off after its next restart.
- **RAM image `0x09B5` and `0x0901` (`F` command, as for the RAM-only targets):** the write is acknowledged and reads back at once. Half a second later the board has put the old value back, and the unit did not change.

The user interface is the master of these user settings: the board takes them from it over and over, and anything written from the X10A port is undone. Switching the operation from a home automation therefore stays with the user interface's path (the Daikin cloud, or a P1/P2 bus adapter). ESPAltherma can read the state; the registers it already polls give space heating on/off and the operating mode.

To confirm one, read the matching screen of the user interface and the address on the same day, and open an issue with both.

## Outputs: the actuator test and the service command `B`

Can the pump and the three-way valve be switched from the X10A port? Tried on an EHBX08EF6V with space heating and hot water switched off on the interface, 17 November 2026. The RAM addresses below were read with the diagnostics page's **Memory read** (command `R`, nothing written there); the port state with the service commands `D` and `S`.

**The interface's actuator test cannot be started from the port.** The installer starts it on the interface ([A.2] Commissioning > Actuator test run). Reading RAM while it ran: the request sits at `0x0864` (`0x0004` for the pump, `0x0020` for the three-way valve), copied to `0x0866` where the board acts on it. But the interface reasserts it a few times a second: a RAM write of `0x0864` was gone after about a second, one of the word `0x090A`…`0x090C` it is built from after 0.2 s, and nothing moved. The test runs only while the interface holds the request, which the port cannot do.

**What moves when the actuator test runs** (read with `D` and `S`):

| What | Where |
|---|---|
| Three-way valve to hot water | port P0 bit 5 (`0x3E0`: `0x85` → `0xA5`) |
| Pump running | port P5 bit 6 (its run request, RAM `0x2DEC` bit 13), and the pump's PWM signal at `0x3AEE`: `0xFFFF` stopped, 29490 (45 %) in the actuator test, as the register *Water pump signal* (44) |
| Flow | the timer word read by `Z` at offset 4 falls from about 1022 to 262 with 9.5 l/min |
| Space heating operation on | port P0 bit 1: on while space heating runs, off in the actuator test with the pump running, so not the pump |

**The service command `B` overrides the outputs.** Besides the known `R`, `F`, `I`, `E` and `L`, the X10A port answers `B` and `S`:

| Command | What it does |
|---|---|
| `B` | frame `0F 42` + 13 data bytes + checksum, answer `42 BD`. Each data byte is one output: `0xFF` leaves it to the unit, any other value forces it, until the next `B` or a restart of the board; nothing on the board's side ends it. |
| `S` | reads seven outputs back: the forced value where one is forced, else the port bit |
| `D` | reads the port registers `0x3E0`…`0x3F4` |

Which data byte of `B` is which output was found by setting one at a time and reading `S`, `D` and the registers back:

| `B` data byte | Forces | Tried |
|---|---|---|
| 0 | the pump's run request (port P5 bit 6, RAM `0x2DEC` bit 13) | yes, see below |
| 5 | the three-way valve (port P0 bit 5): 1 hot water, 0 space heating | yes |
| 7-8 | the pump's PWM word `0x3AEE`, high byte first | yes, with byte 0 |
| the others | outputs and requests not identified | no |

What happened:

- **Three-way valve:** byte 5 = 1, the rest `0xFF`. The port bit went to hot water at once and the register *3way valve* followed at the next poll. `B` with only `0xFF` put it back.
- **Pump, byte 0 alone:** the run request was set and the register *Water pump operation* showed ON, but the PWM word stayed at `0xFFFF`. The pump stood still: 0 l/min, signal 100.
- **Pump, byte 0 with bytes 7-8 = `73 32`:** the pump ran at 9.5 l/min, signal 44, until released. Three minutes after this run the unit raised **C0-00 (flow sensor error)**. Its own control had the pump off and the flow sensor reported flow: the unit took the sensor for faulty. The error was reset on the interface and did not come back.

**Do not force the pump this way** while the unit has its own pump off. Forcing the valve showed no error in one try, but the unit's control does not know about it either: during a run of its own the heat would go where the valve points. Neither is used by ESPAltherma.

## Lower hot water targets through the RAM curve

An EHBX08EF6V, 12 November 2026, hot water on and weather dependent. Both curve words were written in the RAM (F command); the memory was never written.

|---|---|---|
| 45 / 45 °C | 45 °C | before |
| 20 / 20 °C | 25 °C | for 180 s |
| 25 / 25 °C | 25 °C | after 2 and 15 s |
| 30 / 30 °C | 30 °C | after 2 and 15 s |
| 35 / 35 °C | 35 °C | after 2 and 15 s |

The memory's curve (indices 366/367, `0x67` / `0x3F`, 60/60 °C) did not change. The unit follows the RAM curve under the settings' minimum (35/45 °C) down to 25 °C: the RAM-only range starts there on this software.

On 16 November, with the tank at 48 °C: a target of 55 °C started a hot water run within 40 s, and a target of 25 °C asked six minutes into it ended the run within 20 s (three-way valve back to space heating, the compressor stopped 40 s later). With 25 °C held the tank went from 66 to 48 °C over a day without a run.

On 17 November the hydro board restarted four times (field settings changed on the interface). Each time it came up with the memory's curve (60 °C) and started a hot water run, the three-way valve on hot water; ESPAltherma wrote the held 25 °C back within 30 to 60 s and the run ended, once after the compressor had run for about 30 s.

## The tank hysteresis from the port

`[6-00]`, the heat pump's ON hysteresis of the tank (in *reheat only*, a run starts once the tank is below the target minus this), is a word at `0x344C` that the board copies to `0x30E6` and `0x3136`. On 17 November, the tank at 46.8 °C, a target of 51 °C set through ESPAltherma (RAM only) and the hysteresis at its setting of 5: no run for 10 minutes, the tank above the ON point of 46. Then `0x344C` written to 3 in the RAM (the copies followed), an ON point of 48: a run started 9 min 54 s later. The target went back to 25 and the hysteresis to 5 a few seconds into it; the memory was not written. The board seems to look at the tank only every few minutes: the scheduled disinfection the same morning started its run 5 minutes after its target. One run, so not a proof that the hysteresis and not a slower check started it, but the 10 minutes before it saw none with the same target.

## The backup heater setting from the port

`[4-00]` (index 402) and a working byte at `0x4E42` both went from 0 to 1 when the setting was set to 1 on the interface. Then, from the port, only towards off:

- RAM byte `0x4E42` written to 0 (F command): it stayed at 0 for 60 s, the image still read 1.
- Index 402 written back to its earlier byte (E command, as for the curve): the memory and its image in RAM read it at once and kept it.
- The interface's settings overview, opened afterwards, showed 1 for about a second and then 0.

So, unlike on/off and the operating mode, the field settings are the board's: the interface reads them from it. Not checked: whether the heater itself follows such a write (it would only run below `[5-01]`, 0 °C here), and a write towards on, which was not made.
